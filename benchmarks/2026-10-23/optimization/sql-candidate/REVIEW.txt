Expected cost reductions (hypotheses until EXPLAIN and measurements):
1. Feed count follows the viewer's follows PK and bounded articles_author_idx probes, with a global1000 cap. This avoids a possible expensive generic semijoin/full article scan. Unique follows prove no article can be counted twice, and limiting each author1000 cannot change min(total,1000).
2. Global/author singleton and nonsharing batched pages carry article row fields out of their first scan instead of re-fetching every returned ID by PK. Test both first pages and nonzero offsets: offset scans carry row data now, so large offsets could trade extra heap access against the eliminated re-fetches.
3. Shared-list mode deduplicates page arguments before pagination and computes each distinct filter's count once, then restores all member ordinals. Every member retains its own favorited/following flags. Existing sharing heuristic stays unchanged.
4. JSON tags use binary text instead of binary bytea after convert_to. On the fixed UTF8 challenge database both wire payloads are identical; the native column reader consumes bytes without OID-dependent logic. Verify Unicode/control-character tags via HTTP and unchanged conformance. The statement output type changes, not the emitted response bytes.
5. Feeds join the existing read pool and use ST_BATCH_FEED34/IIII for groups; every request retains its own count, page, viewer and ordinal. No assumed viewer-independent feed overlap.
6. Comments join the pool with a32-member bound and ST_BATCH_COMMENTS35/Ia. Distinct slugs materialize at most100 correctly ordered comments/author rows once; unique nonanonymous viewers read their followee arrays once. Unknown slugs produce no row (404), while existing empty articles emit one NULL-comment row ([]). Final rows order by member ordinal then created_at/id descending. Metadata and followee arrays exist only within the active SQL execution; no result is retained for another execution.

No schema/index/PG-setting change. JWT signature/expiry checks, bcrypt cost10, mutations/commit handling and the committed-favorite correction are unchanged. FAV_LATERAL is unchanged: compare its bool_or heap fetches against separate COUNT index-only + viewer PK EXISTS before deciding whether another candidate is justified.
