# Powered Goose110k collapse diagnosis

The110k phase suffered a real end-to-end collapse:127,989 measured request timeouts (10.90%), across all21 endpoint families, and206,699 errors in all native timeline buckets. Native samplers also stalled, so the phase is **INVALID_GENERATOR plus FAIL_SLO**. It supplies no valid capacity bound, and invalid client timing does not exonerate the application. The initiating cause is unresolved.

At100k, this exact binary/session completed26,474 req/s with zero errors and p95/p99 of6.603/46.751ms. At110k it initially sustained about29k completions/s, then all shards worsened aroundt90–91 (16:05:58UTC). Sampler delays and completion collapse followed at t91–92; the first recorded timeout appears at t102. Aggregate p99 is22.643s and maximum40.239s. These are client-observed durations under invalid scheduling, not isolated server service times.

Both cgroups show rising CPU pressure despite staying below their individual8CPU average limits. They share one10-logical-CPU VM; quotas do not reserve cores. The six client shards eventually report5.8–25s sampler delay. Target app PIDs remain stable, no target/client swap or OOM occurs, and the post-load health request succeeds. The full-window PG CPU component is withheld because transient backend population changes; no new backend appears at the initial t90–92 collapse.

The outer Mac is not a quiet-memory control. Its compressor occupies about12GiB near onset. Exact t90 sampling records6,489 compressions and8,141 decompressions (~127MiB decompressed), a localized event coinciding with early latency rise. Host swap usage remains1,890.81MiB with no new Swapouts. Guest memory PSI remains zero. This makes outer-host compression a plausible contributor, not a proved cause or evidence of application memory exhaustion.

PostgreSQL logs contain no errors, deadlocks or statement cancellations in the scoped window. The preceding checkpoint finishes at16:05:46.371; the next starts at16:06:16.515, roughly17.6s after collapse onset. Therefore that new checkpoint cannot explain the initial trigger. Its46s write interval is paced checkpoint elapsed time; sync is.001s. No transaction rollback/deadlock/temp-file/checkpointer statistics, SQL waits, query durations or table-growth counters were saved, so those cannot be reconstructed or ruled out.

The application has a concrete overload amplification risk: full read pools bypass the in-flight gate, PostgreSQL queues have no admission/byte limit, and already-pipelined work remains after clients disconnect. The phase makes247,457 TCP dial attempts for110,000 VUs. Retry/obsolete-read work can prolong a slowdown, but queue counters were not recorded, so this is not proof that the application initiated it. Bcrypt alone cannot explain all21 endpoint families failing.

After the current control completes, the bounded next diagnostic is one fresh, separately labelled reproduction of the same10k warmup→100k→110k continuous session, unchanged app binary/source and GOMAXPROCS1, with client GC logs and per-process CPU, host/cgroup pressure, PostgreSQL activity/waits and before/after transaction/temp/deadlock/checkpointer counters. Only a reproduced event justifies a second client-GOMAXPROCS2 diagnostic; that changes generator metadata and cannot qualify under or repair the frozen capacity protocol. An independent external Linux client remains the appropriate capacity control. Application queue changes should follow observed service-side backlog, preserving committed-write semantics.

All analysis used saved files and source only. No Docker, database, build, benchmark or source mutation was performed. The JSON preserves endpoint data, exact onset, host counter chronology, monitor windows and input hashes.

Client source confirms that the nominal 10-second deadline covers socket I/O; measured duration also includes resumed goroutine scheduling and synchronous response/JSON processing. A transport error closes the VU socket, and the next component can immediately redial. The tcp_connects field counts attempts before Dial. Endpoint-window accounting uses request start time, whereas timeline error buckets use completion time. Late sampler catch-up can misalign histogram buckets; zero timeline quantiles under that stall do not indicate zero-latency service. None of this proves GC or removes the observed user-visible failure.

The native sampler also reaches its hard stop with 24,232 VUs still active across the six failed shards. Recorded error totals do not show that every started request finished; unfinished work is censored.
