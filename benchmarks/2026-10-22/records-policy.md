# Local validation and measurement records

This is an ARM64 Mac/Docker lab comparison, never an official leaderboard score. The previous one-core SQLite/wrk challenge is a different workload. The new app and PostgreSQL 18 must share one container with an eight-CPU CFS quota, 16 GiB memory cap and zero swap allowance. No explicit cpuset or affinity. Generator processes run outside that shared budget with their own recorded limit; all still compete on the same physical Mac. Capture host pressure and Docker VM resources so physical contention is visible.

Use the unmodified upstream 197-step suite, seed generator, load generator and merging rules. Freeze the upstream commit, every submission file, compiler and binary before comparing. Record the Docker image ID, full HostConfig, architecture and all relevant version/configuration files. Do not include `.goose` compiler checkout or generated binaries when declaring application source hashes, but retain compiler commit and binary hashes separately. The setup script requires a real Go 1.27.1 or newer; the module must not be downgraded to fit an old installed Go.

The seed scripts destroy only their named `conduit_dev` or `conduit_seed` database inside the owned container. They verify every reference row-count and fingerprint. Dev seed retains all 100,000 users and 200 tags but scales the remaining tables to about 2%; it cannot establish capacity. Retain the final `OK` line and complete fingerprint check. Every conformance invocation clones its chosen template through the original `test/run.sh`; use both templates. Run build/start under the normal application user and preserve the exit status. Source folders must be writable by that user for compiler checkout/output; arrange that when staging a copy into the container.

`box/pg-conf.sh` reads `nproc` and `/proc/meminfo`; those reflect the Docker VM rather than cgroup quota/cap. `setup-container.sh` therefore renders the same public formulas with inputs of eight CPUs and 16 GiB, without changing upstream files. `work_mem = floor(floor((16777216-4194304)/(108*3))/4) = 9709 kB`; all other values match the official eight-core case. Record both source hash and live `pg_settings`. No schema/index/server-settings changes beyond this fixed baseline, and no runtime host tuning. Allowed app session settings must be recorded separately.

Retain every attempted candidate/control run, including errors, failed probes, startup failures and generator-limited runs. Never replace failing trials or cherry-pick retries into an average. Each attempt gets a unique immutable directory and run ID. Freeze source/binary hashes, database clone name and template, all generator arguments, start time, raw per-shard JSON, merged output, server logs, cgroup CPU/memory/oom statistics and host/guest pressure witnesses. Secret values are benchmark fixtures, never real credentials.

For capacity evidence, use normal think-scale 1, full seed, the repository three-minute warmup, 60-second ramp + 60-second measured probes, and 60-second ramp + 300-second measured holds. Search probes and holds intentionally share the grown database after the initial fresh clone. A fresh clone for every probe is a separate diagnostic protocol. Keep all tail requests draining before the next phase. All native SLOs must pass: p95 <500 ms, p99 <1000 ms, errors <1%; retain per-endpoint results too. Generator-limited is invalid, not an app failure: merge flags CPU >75%, timer lag, missed active population and scheduling delay. Record Mac/VM memory pressure as additional validity evidence without inventing post hoc exclusion rules.

Compare against pinned official Rust PR #7 head and, if practical, pinned open Goose PR #31 head. Repeat adjacent or alternating controls before claiming a local improvement. Do not count throughput-only smoke tests or accelerated think-scale tests as a challenge score. The official place #1 can be established only by the maintainer's eight-core x86-64 full-seed external-generator benchmark; current official score to exceed is 100,000 concurrent simulated users. Above 100,000 VUs, the generator reuses seeded accounts, so this is not a count of distinct identities.

Port scaling: macOS has roughly 16,000 ephemeral ports; direct native-Mac generators are unsuitable for the target. Linux generators also need enough source addresses/target IPs to avoid a roughly 64k TCP connection tuple limit, plus documented `nofile` and port-range settings. Any permitted load-machine tuning belongs outside the combined server budget and must be recorded. Configure these before load, never silently retry connection failures away.

The setup scripts are prepared only. Running them requires the root agent's selected owned container and correct `REPO_ROOT`, `EVIDENCE_ROOT`, `APP_USER` and PATH. They do not provision a cloud machine or incur spend.
